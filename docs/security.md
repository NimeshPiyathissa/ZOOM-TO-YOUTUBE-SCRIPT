# Security model

## Network exposure

`ufw` allows inbound SSH only. The dashboard (`127.0.0.1:8443`) and `x11vnc`
(`127.0.0.1:5900`) are loopback-bound — neither is ever directly reachable without
a tunnel. See [remote-access.md](remote-access.md) for SSH tunnel / Tailscale /
Caddy options and their trade-offs.

## Secrets at rest

See [encryption.md](encryption.md) for the full design. Short version: every real
secret (stream key, Zoom passcode, VNC password, Telegram credentials) lives in an
AES-256-GCM-encrypted vault, keyed by an argon2id-derived master password never
stored anywhere. Non-secret config stays in plain files.

## Cross-user privilege boundary

The dashboard runs as an unprivileged `dashboard` system user; the streaming
pipeline runs as a separate `zoombot` system user. The dashboard never runs
arbitrary commands as `zoombot` — it has a narrow, explicit sudoers allowlist
(`/etc/sudoers.d/dashboard`, regenerated by `install-dashboard.sh`) naming exact
scripts and exact `systemctl` unit/verb pairs, nothing else. Every value that
crosses that boundary (a URL, a config value, a watermark image) is piped in on
stdin, never interpolated into a command line or passed through a shell — see
`scripts/write-env.sh`'s and `scripts/write-source.sh`'s headers for the
NUL-delimited wire format this relies on, and
`dashboard/tests/test_env_parser_roundtrip.py` for the test proving the writer and
both readers (`scripts/lib.sh`'s bash reader, `app/env_store.py`'s Python reader)
agree, including for values containing `$`, backticks, and `;` — none of which are
ever expanded or executed, because nothing here uses `source`/`eval` on
dashboard-supplied content.

## URL security (webpage / direct sources)

Every URL for a webpage or direct-media source is checked in `app/url_security.py`
before it's saved, and again immediately before it's written to
`current-source.env` (DNS can rebind between save-time and launch-time). Rules:
only `http`/`https`/`rtmp`/`rtmps`/`srt` schemes, further restricted per source
type; every resolved address (not just the first) is checked against loopback/
link-local/private/multicast/reserved ranges for both IPv4 and IPv6, including the
`169.254.169.254` cloud metadata address explicitly; `localhost`/`*.localhost`/
`*.local` are rejected before DNS resolution is even attempted; a URL beginning
with `-` is rejected outright and every URL reaches `ffmpeg`/Chrome as a single
`argv` element, never through a shell.

IMDSv2 (`HttpTokens: required`) should be enforced at the instance level as
defense in depth beneath the metadata-address block above — verify with
`aws ec2 describe-instances --instance-ids <id> --query
'Reservations[].Instances[].MetadataOptions.HttpTokens'` (should print
`"required"`), or from the instance itself: an unauthenticated `GET` to
`http://169.254.169.254/latest/meta-data/` should return `401`.

## What's never logged

Stream keys, passcodes, tokens, and the VNC password are never written to logs or
API responses in plaintext. `ffmpeg.log` does contain the full YouTube RTMP URL
(stream key and all) in FFmpeg's own startup output — that file stays
group-readable-only (`chmod 750` on its directory), never world-readable, and the
dashboard always redacts before displaying log content in the UI. If you ever pull
`ffmpeg.log` off the box directly (bypassing the dashboard), treat it as containing
a secret.

## Why the public setup script can't be password-gated

An earlier iteration of this project tried to gate `install.sh` itself behind a
password check. **This doesn't work in a public repository** — the check, and any
embedded value it compares against, are readable (and deletable) in the source the
moment the repo is public. That script was removed, not extended. If you want real
access control over *who can obtain the code*, the answer is a private repository
with invited collaborators — GitHub/GitLab access control is a different, actually
effective mechanism, because it gates the repository itself, not a check inside
code anyone with the repository can already read. The Master Encryption Password
(Part 0) is a genuinely different thing from this and remains fully effective,
because it protects data at rest on a machine, not access to source code.

## Reporting a security issue

Open an issue, or if it's sensitive, contact the maintainer directly rather than
filing a public issue with exploit details.
